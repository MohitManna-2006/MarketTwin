# Phase 3B AI research

## Metric planning and correction

Executable comparison metrics are the fixed identifiers in `core/src/experiment/experiment.cpp` (`kMetrics`). The model-facing schema enumerates these identifiers, and a regression test compares the enumeration with the native golden experiment result. “Inventory risk” remains an analysis topic: `mean_abs_position` and `max_abs_position` are inventory-exposure proxies, not a complete risk measure. If a model returns an unknown identifier, the backend records its exact spelling, requests one correction, and validates again. A second invalid proposal returns `UnknownMetric` with the rejected identifier and supported catalogue. The correction cannot change the scenario, agent, or seed count. Planning and correction never submit a simulation.

## Local setup

Build the native Python binding and start the API using the Phase 3A instructions in `README.md`. Set `MARKETTWIN_AI_MODEL` and `MARKETTWIN_AI_API_KEY` in the API process environment. The default provider is an OpenAI-compatible Chat Completions endpoint at `https://api.openai.com/v1`; change `MARKETTWIN_AI_BASE_URL` for another compatible service. Optional settings are `MARKETTWIN_AI_TIMEOUT_SECONDS` (default 30) and `MARKETTWIN_AI_MAX_SEEDS` (default 100). Set `MARKETTWIN_AI_INPUT_USD_PER_MILLION_TOKENS` and `MARKETTWIN_AI_OUTPUT_USD_PER_MILLION_TOKENS` to your provider’s current rates if you want per-request estimated USD cost in tool events; otherwise token usage is recorded without a price estimate. Do not put the API key in the web app environment. The browser calls only MarketTwin's FastAPI service.

Open **AI Research** in the terminal. Ask for a paired baseline versus inventory-aware maker comparison in a named scenario and specify seed count. Review the exact plan and its digest, then choose **Approve & run**. Approval is stored server-side before the existing native experiment API is invoked. The report's numeric table comes from the native `experiment.json`; selecting a row exposes its evidence reference. A verified Markdown download is available from the report. The linked Experiment Lab can materialize an individual cell and request replay verification.

## Supported operations

The executable intent is a paired policy comparison within one catalogued scenario. The planner checks scenario, subject maker, metrics, seed count, run budget, and native experiment validity. The native statistician computes candidate minus baseline, Student t intervals, and bootstrap intervals. A completed paired experiment can also be attached for read-only report generation, with no approval or new simulation. Paired seeds and replay status can be inspected through the linked API/UI. The AI planner does not yet construct a shocked-versus-unshocked native comparison. It returns `UNSUPPORTED` or an explicit validation error for requests outside this design.

The internal typed read-only tool registry allows scenario listing and inspection, native experiment validation, experiment status and results, paired seed inspection, registered run and agent metrics, and replay status. It rejects arbitrary paths and unsupported operations, authorizes evidence against the investigation's experiment, caps each response at 256 KB, and limits an investigation to 64 recorded tool calls. Experiment submission is intentionally available only through the trusted approval transition.

The current investigation endpoints are `/api/v1/ai/investigations` and `/{id}` with `/plan`, `/approve`, `/reject`, `/cancel`, `/status`, `/report`, `/report/markdown`, `/messages`, `/tool-events`, and `/seeds/{seed}`. The model never receives a tool that bypasses approval. Each event records wall-clock time, stage, operation, status, and safe metadata. Simulation time is recorded only by the native engine. An interrupted process marks unfinished work as failed or resumes report construction from an already completed native experiment.

## Evaluation and limits

`uv run pytest -q tests/test_ai.py` runs 54 deterministic evaluation cases. They include valid plans, invalid scenarios and metrics, seed caps, unsupported intents, ambiguity, provider outage, approval enforcement, native execution, claim tampering, seed inspection, follow-up, and numeric hallucination rejection. CI uses a deterministic mock model but invokes the native C++ experiment runner in the integration case. Live-model evaluation requires a configured provider and is intentionally separate from CI. This environment has no provider credentials, so no authenticated live-model result is recorded here.

The Playwright test suite sets `MARKETTWIN_AI_PROVIDER=fixture` and `MARKETTWIN_AI_MODEL=deterministic-fixture` for its exact `[E2E fixture]` request. That adapter exists only to make browser CI deterministic; it rejects other requests and is visibly identified as a fixture in investigation metadata. It still uses the real API, SQLite workflow, and C++ engine after approval. The [native demonstration](experiments/phase3b-native-demo/README.md) records a separate completed fixture-assisted experiment and replay.

On the development machine, all 54 deterministic research cases, four provider transport and schema cases, and the remaining API tests passed (93 Python tests total). The C++ release preset passed 209 tests, the frontend passed 60 Vitest tests, and Playwright passed 11 end-to-end tests including the AI workflow and an axe audit of its report. These are fixture-based reliability measurements, not a measured live-model planning success rate.

The backend permits at most 100 paired AI seeds by default, 32 active investigations, 30 conversation messages per investigation, 2,000 characters per question or follow-up, and its existing bounded native job queue. The provider uses three total attempts for transient errors and a fixed token cap. New executions always need the digest-bound approval transition. The local API remains single-user and unauthenticated; use a trusted local environment.
